## What the schema inspection found

See `README.md`'s "Data" section for the full write-up. Highlights:

- Live node count is 5 (node_id 1-5 in `sensor_calibration`), not the
  brief's "four" -- verified from data, not assumed either way.
- `readings` has an `is_backlog` column `ml/option_one/data_supabase.py`
  doesn't fetch or use. Using it fixed a real timestamp bug: one node-1
  row's `recorded_at` decodes to 2024-04-24 (a stale RTC value) against a
  `received_at` of 2026-07-03, and passes `option_one`'s bare `>2020`
  plausibility check anyway. Fixed here with a gap-from-`received_at`
  check, tightened for non-backlog packets (near-zero expected gap) and
  loosened for backlog ones (up to 90 days, matching observed real
  backlog delays up to ~37 days).
- `sensor_calibration.GPS` gives real per-node coordinates, used to fetch
  each node's own Open-Meteo weather + elevation, rather than one shared
  site point.
- Soil moisture is raw ADC counts (`readings.raw`) -- modeled directly per
  the brief's instruction not to invent a calibration curve, even though
  an existing air/water linear transform is available in
  `sensor_calibration` (that's `option_one`'s approach, not used here).

## Feature-table design decision (made instead of pausing to ask)

Built per the brief's explicit feature list (lags, rolling rain/ET0 sums
and their difference, days-since-rain, rolling temp/VPD, day-of-year
sin/cos, node ID, elevation where available) -- this list was specific
enough that there wasn't a real design choice to surface, just
implementation decisions:

- Rolling windows computed on weather extended 90 days before each node's
  moisture record starts (fetched separately), so early rows aren't
  silently missing long-window features -- see README "Feature table".
- Slope/aspect skipped (not available anywhere in this repo); elevation
  included (available from Open-Meteo's response per node coordinate).
- No calibration curve applied to `raw` -- modeled directly per the
  brief's own explicit instruction, not a judgment call.

## Persistence comparison results

Chronological CV: loses to persistence at every horizon (h=1/7/14/28).
Leave-one-node-out: beats persistence at h=7 (marginally, 319.8 vs. 328.9
RMSE) and h=14 (clearly, 382.7 vs. 472.1), loses at h=1 and h=28. Full
numbers and the CV-vs-LONO disagreement explanation are in README.md's
top section, by design (not buried). h=28's chronological CV result (6
test rows across 2 folds) is flagged as too thin to trust either way.

## What I'm unsure about

- **h=28's chronological-CV number is close to meaningless** (2 folds, 6
  test rows) -- a direct consequence of the deployment record being only
  ~2 months deep, not something more data engineering could fix within
  this task. Flagged prominently in README rather than hidden in a
  footnote.
- **SHAP importance concentration is extreme** -- as few as 1 of 46
  features carries any signal at h=28. With 49 effective independent
  events total across all nodes and horizons, I'm not confident these
  rankings would survive even a modest amount of additional data; treat
  "rain_sum_14d dominates at h=14/28" as a plausible-and-not-obviously-
  wrong result, not a validated physical finding.
- **The 8.8% duplicate-packet rate vs. option_one's documented ~16%**:
  I believe this is just table growth diluting an unchanged absolute
  duplication mechanism (reasoned through in README), not a sign the
  underlying bug was partially fixed since `option_one/README.md` was
  written -- but I did not verify this against `option_one`'s git history
  or the actual dates behind its 16% figure, since that would mean poking
  at `option_one`'s numbers rather than treating this pipeline as fully
  independent of it. Worth a second look if this rate matters to you.
  Nothing to reconcile.
- **No live third baseline against `ml/option_one/bucket_model.py`** --
  documented as a deliberate scope decision in README "Known limitations",
  not an oversight. Running it properly means re-running its own
  differential-evolution calibration per node, which has its own
  multi-minute runtime and its own output artifacts; doing that inside
  this task risked producing a second, silently-diverging "official"
  bucket-model result rather than reusing whatever `option_one`'s own
  authoritative run already says. The brief's phrasing ("if you use it")
  reads as optional, so I documented rather than ran it -- flagging in
  case that reading was wrong.
- **Raw-ADC glitch reads** (0.1-9% of readings per node, outside the
  sensor's own `[water, air]` calibration bounds) are diluted into daily
  means, not filtered -- per the brief's "keep it raw" instruction, but
  worth knowing this noise source is still in there unaddressed.
- **`predict.py` doesn't call the Open-Meteo forecast endpoint** -- a
  reasoned decision (the feature set is entirely backward-looking, so a
  forecast isn't actually needed as a model input), not a shortcut, but
  flagged in case the intent behind the original spec's "load model +
  forecast weather -> prediction interval" line was for forward-looking
  weather features that never made it into this build -- see README
  "Known limitations" for the full reasoning and the seam to extend if so.
